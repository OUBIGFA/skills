# 实战踩坑手册（proxy-geo-rename）

来自一次 38 节点真实检测的完整踩坑记录。每条按"现象 → 原因 → 对策"组织。

## 1. 本机代理客户端的 TUN 全局接管污染一切

**现象**：本机直连测"法兰克福锚点 1ms"（物理不可能）；或检测结果疑似全走同一出口。
**原因**：客户端（karing/Clash Verge 等）开启 TUN 模式后，虚拟网卡接管全部流量，包括测试脚本的出站与"直连"测量。TCP 握手被 TUN 本地完成再中继，直连 RTT 全是假的。
**对策**：
- 测试配置的 `route.default_interface` 绑定物理网卡（probe.py 的 `--iface`），出站绕过 TUN
- 凡本机直连做的测量，先做物理合理性检查（大陆到欧洲 <150ms 即为假）
- 判断依据：`Get-NetAdapter` 有状态 Up 的 TUN 虚拟网卡即需处理

## 2. 代理的"延迟拨号"让建连计时全部失效

**现象**：通过代理 CONNECT 各锚点全部 0ms。
**原因**：sing-box 收到 CONNECT 立即回 200，实际出站连接推迟到首个数据包才建立。测"CONNECT→200"只测了本地回环。
**对策**：在隧道内做**真实 TLS 握手**计时（latency_arbiter.py 已实现）——握手必须与目标真实往返，无法被提前应答伪造。

## 3. 新版配置字段喂给旧内核会连环报错

**现象**：`unknown field "tls_tricks"`、`unknown uTLS fingerprint: custom` 等 FATAL。
**原因**：GUI 客户端（karing 等）导出的配置含新版/私有字段（`domain_resolver`、`tls_fragment`、`tls_tricks`、指纹值 `custom`），旧内核严格解析直接拒绝。
**对策**：probe.py 的 `strip_unknown_fields` 循环——按报错路径逐个剥离未知字段（均为非连接必需项）、不支持的指纹值回退 `chrome`，直到 `check` 通过。新遇到的值类错误按同模式加分支，不要手工逐个删。

## 4. DNS 语法随内核版本分裂

**现象**：1.10 内核不认 `{"type":"udp"}` 新式 DNS；1.14+ 将移除旧式。
**对策**：probe.py 按 `sing-box version` 自动选择：≥1.12 用新式（含 `route.default_domain_resolver`），否则用旧式 `{"tag","address","detour"}`。

## 5. 首轮"离线"可能是并发误伤，但两轮仍离线就是真死

**现象**：首轮高并发测活时 hysteria2/tuic（UDP 协议）节点成批离线。
**原因**：并发抢带宽 + UDP 握手对丢包敏感。
**对策**（已内置）：首轮按 `--alive-workers`（默认 16）并发测活，每节点最多 3 次、轮换 Google/Cloudflare/Apple 三个端点，全部失败才判不通；首轮不通的节点进入第二轮，以 4 并发直连复测（复测通过按直连处理，不判落地），本地同时经最多 3 个不同服务器的已判活前置链式测活。两轮直连与经前置都不通才淘汰。经验数据：首轮离线的节点复测后极少复活，两轮仍不通的按死节点处理。mihomo 日志可看具体错误：`i/o timeout`=服务器不通/被墙；TLS/握手错误=传输层配置或服务端问题。

**补充：服务检测通过、测速时"读超时"淘汰**：节点在服务检测阶段可用、测速时 0 Mbps 并报 `Read timed out`，多为节点本身间歇掉线。可单独对该节点多轮测活并换多个下载站（Google、Cloudflare、GitHub、CacheFly）对照：若对照节点正常而该节点连 `www.google.com` 都不通，即为节点失效，淘汰正确。

## 6. ip-api 的中文城市名会"张冠李戴"

**现象**：多数库判波兰华沙，结果城市却显示"斯德哥尔摩"。
**原因**：ip-api 对该 IP 判国为瑞典、城市斯德哥尔摩；旧逻辑把 ip-api 的中文城市直接当作胜出英文城市（Warsaw）的翻译用。
**对策**：verdict.py 已修复——ip-api 的中文城市仅当其国家判定与多数票一致时才作为中文名来源；英文城市中文化靠内置映射表。

## 7. 城市名中英文/全称简称分裂票仓

**现象**："Warsaw"2 票 + "华沙"1 票 + "Frankfurt am Main" vs "Frankfurt"，各自成桶导致多数判定失真；"台北市"与"台北"分组分裂编号。
**对策**：verdict.py 的 `city_key`：英文名先经映射表转中文再聚合，中文名裁行政尾缀（市/县/都/府/州/区），同城必同桶。

## 8. 数据库分歧 IP：五库五说是常态，不是错误

**现象**：同一 IP，Cloudflare 说 DE、ip-api 说 SE、MaxMind 说 US、ipwho 说 AT、供应商叫 Poland。
**原因**：新分配段、跨国租用、geofeed 声明与物理部署不一致，各库更新节奏不同。
**对策**（按序）：
1. recheck.py 补 3 库扩大票池，多数常会浮现
2. 仍无多数 → 延迟仲裁物理测距（见 SKILL.md 步骤 3 解读要点）
3. 裁决原则：**库有明确多数从库**（网站眼中的位置，决定实际使用体验）；**无多数从物理**（colo + 延迟梯度）
4. 终裁写 overrides.json，并在 note 里记录依据（报告透明可查）

## 9. Anycast/CDN 节点是"双出口"，位置天然流动

**现象**：同一时刻 Cloudflare trace 看到的出口 IP 与其他 4 源不同（split_exit=True）；第二轮出口又变了（exit_stable=False）。
**原因**：节点经 CDN 中转，对不同目标网站分流不同出口；Anycast IP 本身多地就近落地。
**对策**：按**主出口**（非 CF 的多数源一致 IP）判定命名；recheck.py 采样出口池记录事实；报告注明"访问 Cloudflare 系网站走另一出口"。colo 与主出口跨洲时只降置信不否决（正是分流的表现）。

## 10. RIR 注册国 ≠ 物理位置，绝不能计票

**现象**：RIPE 注册显示 US 的段，物理和多数库都在欧洲。
**对策**：注册地信息挂 `ref:` 前缀存入 sources，verdict 自动跳过计票，仅在报告中展示供参考。

## 11. 补充地理库经常到不了票，属正常

**现象**：ipapi.co / ipapi.is 无响应（限速或大陆不可达），只有 freeipapi 到票。
**对策**：缺票可接受（fetch 失败返回 None 即缺票），不重试轰炸；这正是设计多源冗余的原因。

## 12. 荷兰小镇类城市名没有通用中文译名

**现象**：四库一致给 "Eygelshoven"（林堡省小镇，机房所在地）。
**对策**：保留英文原文命名（如 `🇳🇱 荷兰_Eygelshoven_1`），报告注明；不硬造音译。常见机房城市的映射表在 geodata.py 的 CITY_ZH，可按需补充。

## 13. 客户端里能用的节点，检测却判"离线"——直连被墙

**现象**：用户反馈某节点在 karing/Clash 里明明能连通，检测却两轮判离线。日志显示 `dial tcp <IP>:<port>: i/o timeout`。
**原因**：节点服务器 IP 从本机**裸连被墙**（搬瓦工等知名 VPS 段常见）。用户客户端开着 TUN 全局接管时，该节点的连接实际经客户端当前路由**隐性中转**后出去，所以"能用"；而检测为绕开 TUN 污染绑定物理网卡纯直连，撞墙即超时。实证案例：SS2022 节点 65.49.197.121:51888 直连 4 次超时，经 karing 本地端口中转秒通，出口即服务器本身（美国洛杉矶，colo=LAX）。
**对策**（recheck.py 已内置）：
- 直连复测仍失败 → `find_local_proxies()` 探测本机代理客户端的端口（枚举代理类进程的监听端口 + 常见端口 7890/7897/2080/10808 等，逐个做 SOCKS5 握手 + 真实出网 204 验证）
- 经前置 `detour` 中转重测；DNS 用 DoH 经前置，避开 TUN 的 DNS 劫持
- 前置优先选 SOCKS5（支持 UDP 转发，能救 hysteria2/tuic）；HTTP 前置只能救 TCP 协议节点
- **中转不影响出口判定**（出口仍是节点自己的出口 IP），复活节点标 `via_front`，报告注明"直连被墙，裸连网络下不可用"——这个信息本身对用户有价值
- 中转也不通才终判死节点

## 14. 检测完成后配置被客户端改名，结果对不上号

**现象**：检测显示某节点已复活并定位成功，rename 却报"离线保留原名"。查配置发现该节点的 tag 已从 `Bandwagon-LA` 变成 `🇺🇸 美国_Bandwagon-LA_USAI❇️`。
**原因**：GUI 客户端（karing 等）在订阅更新或节点测试时会自动重写 tag（加国旗/地区前缀）。早期实现按 tag 关联检测结果与配置节点，名字一变即断链，结果被当成"没检测过"。
**对策**（common.py `pair_nodes`）：三级关联，指纹 → 名字 → 位置。
- 指纹 = `协议|服务器|端口`，不受改名/调序影响，是主关联键（probe 会写入结果文件）
- 名字兜底：兼容无指纹的旧结果文件
- 位置兜底：结果数与节点数相同时按序配对
- 配对后回填指纹到结果文件，后续步骤永久免疫改名
- 终裁 overrides.json 同时接受当前名与检测时原名

## 15. 国家中文名要用规范简称，别用地理库的官方全称

**现象**：命名出现 `🇷🇺 俄罗斯联邦_圣彼得堡_1`、`🇰🇷 韩国_首尔特别_1`。
**原因**：早期逻辑优先采用 ip-api 返回的中文国名（官方全称"俄罗斯联邦"）；韩国城市 "Seoul特别市" 裁尾缀时只裁了单字"市"，剩下"首尔特别"。
**对策**：国家中文名以内置 `COUNTRY_ZH` 规范简称为准，地理库返回值仅在表中查不到时兜底；城市尾缀改为先长后短匹配（特别行政区/广域市/特别市…再到单字市县都府州区）。

## 16. 改名后导回客户端，大量节点显示不可用

**现象**：检测证明 34 个节点都能连，用户把配置导入 karing 后几乎每个节点都亮红色警告。
**原因**：用户手上的配置文件是客户端**"导出配置"给出的运行时快照**，不是订阅配置。快照里带着客户端自己的运行时产物：
- `inbounds` 监听 127.0.0.1:3065/3066/3067 —— 正是 karing 自己当时占用的端口，导回去等于让它和自己抢端口
- `dns` 里的 fakeip 服务器、`experimental` 里的 clash_api/统计/缓存
- 遥测与自家域名规则（sentry.io、karing.app、ipcheck.ing）
- DNS 规则里硬编码着导出那一刻的公网 IP（`client_subnet`）
客户端导入后会在外层再包一遍自己的入站/DNS/路由，双层冲突导致内核起不来，于是"所有节点"都测不通——**与节点本身和改名都无关**。
**识别**：配置里同时出现 `inbounds` + `experimental` + fakeip 类 DNS，基本可断定是运行时快照。
**对策**：用 `scripts/make_profile.py` 生成只含节点本体的干净配置再导入；顺带剥离节点上的 `domain_resolver`（它指向快照内部的 DNS 标签，脱离快照即为悬空引用）。入站、DNS、路由一概不写，交给客户端生成。
**正确做法**：改名应作用于**订阅/节点清单**，而不是运行时快照。

## 17. 客户端定制字段不是错误，别删

`tls_tricks`、`tls_fragment`、指纹 `custom` 等是 karing/hiddify 定制内核的私有扩展。官方 sing-box 校验会报"未知字段"——**这只说明官方内核不认识，不代表配置有问题**。检测时可临时剥离（见第 3 条），但生成给用户导入的配置必须原样保留，否则会削弱其伪装能力。

## 18. 域名型节点的解析器指向境外明文 DNS 会失败

**现象**：服务器写域名（非 IP）的节点在大陆环境时通时不通。
**原因**：快照里节点的 `domain_resolver` 常指向一组明文 UDP 的境外 DNS（8.8.8.8/208.67.x），大陆环境下 UDP 53 出境查询易被污染或丢弃，域名解析失败即连不上。本例 38 个节点中有 11 个是域名型。
**对策**：干净配置不写 `domain_resolver`，由客户端用自己的解析策略处理；若必须自定义，改用加密解析（DoT/DoH，如 `tls://223.5.5.5`）而非明文 UDP。

## 19. 写回必须结构化替换 + 保持文件风格

**要点**：
- 改名要同步全部引用点：组的 `outbounds`/`default`、节点 `detour`、`route.final`、`route.rules[].outbound`、`dns.servers[].detour`——遗漏任何一处配置即坏
- 不做全文文本替换（节点名可能是其他字符串的子串）
- 保持原文件换行风格（CRLF/LF）与末尾换行，避免无意义 diff
- 写回后必须校验：JSON 可解析、tag 无重复、所有组成员存在
- 写回前先备份带时间戳的副本

## 20. 落地节点（链式/前置跳板）握手延迟与探测超时的致命矛盾

**现象**：探测结果中“落地节点”一个都没有，哪怕原本在客户端中能正常中转的节点也全部被判定为“直连与前置均不可达”。
**原因**：
- 直连节点为 1-hop 链路，TCP + TLS 握手通常可在 0.5s~1.5s 内建立；
- 落地节点为多跳链式链路（本机请求 -> 本地 mihomo/sing-box 监听 -> 前置 (Key、备用前置或本机客户端端口) -> 远程服务器 -> TLS/Reality 握手 -> 目标网站）。实测该多跳代理链的建连需要 **2.3s ~ 3.5s**。
- 若探针将超时固定设为较短的阈值（如 1.8s~2.0s）或全局设置了短的套接字超时（如 `socket.setdefaulttimeout(2.5)`），所有的落地探测请求在多跳握手完成前就会被主动打断（`ReadTimeout`），导致落地节点 100% 被误杀淘汰！
**对策**：
- **差异化超时**：直连探测保持 2.0s~2.5s（快速排除不可达）；经前置重测的落地探测必须放宽至 **4.0s~5.0s**。
- **全局套接字保护**：底层 `socket.setdefaulttimeout()` 必须至少设为 **6.0s**，绝不能低于 5s。
- **轻量端点优先**：初始探活优先采用 `http://api.ipify.org` 或 `http://ipv4.icanhazip.com`，省去二次 SSL 往返，节省 1.0s+ 宝贵握手时间。

## 21. 并发探测中的顺序阻塞与全局批次死线陷阱

**现象**：整批节点（如批次 02~22）全部报 0 合格，耗时刚好卡在全局批次设定的 deadline（如 15.0s）。
**原因**：
- 采用 `for fut in futures.items(): fut.result(rem)` 顺序遍历并计算剩余时间。若前几个节点为死节点且耗尽了单节点超时，循环刚走到第 3、4 个节点时剩余预算就变为 `<= 0`。
- 此时后续 20~30 个节点哪怕后台已经握手成功，也会在 `fut.result(timeout=0.05)` 中被判定为 `TimeoutError` 强制淘汰并强行 kill 内核！
- 同时，批次过大（如 35~50 节点并发）会导致 Windows 本地 TCP 端口和队列饱和拥塞。
**对策**：
- 严禁对 futures 列表做顺序阻塞遍历！必须采用 `concurrent.futures.as_completed(futures, timeout=...)`，谁先完成谁先产出。
- 批次大小建议控制在 **15 ~ 20 节点/批**，批次等待上限建议设为 35s~45s。
- 退出清理时，必须**先 kill 内核子进程**（`proc.kill()`），使本地监听端口立即关闭并向挂起线程发送 TCP RST，然后再执行 `pool.shutdown(wait=False, cancel_futures=True)`，彻底防止线程卡死拖垮 Python 进程。

## 22. Google 属地探测的 Stream 挂起陷阱

**现象**：探针在探测 Google 属地（Gemini 页面）时偶发全局卡死，直到几分钟后超时。
**原因**：Gemini 首页体积约 825KB。若使用 `session.get(url, stream=True)` 后调用 `resp.raw.read(1024*1024)` 尝试一次性读取 1MB，在 HTTP Keep-Alive 连接下，服务端传输完 825KB 后不会主动关闭套接字，客户端读取 1MB 会持续阻塞在剩余字节上，直到连接超时。
**对策**：
- 直接使用 `resp.text` 读取完整响应（内部由 requests 处理 chunked 编码与 Content-Length，瞬间完成）；
- 或在 `resp.raw.read()` 时使用小 chunk 循环并检测 EOF。

## 23. 测速防断流阈值切勿设过高以致误杀可用低速节点

**现象**：大量连通性良好的节点被判定为“断流假死”淘汰，导致合格率极低。
**原因**：旧版测速逻辑设定了“3秒内不足 300KB（即 100 KB/s）视为断流假死”。但在免费订阅或国际跨洋链路中，大量节点实际带宽在 20~80 KB/s，这对于文本 AI 对话、网页轻量浏览和 DNS 查询完全可用。
**对策**：
- 防断流判定应重点检测“是否完全建立真实数据流”。两条流水线统一为 **3 秒窗口内累计不足 16KB** 才判断流假死（`DEFAULT_STALL_MIN_BYTES`），不以吞吐高低淘汰可用低速节点。
- 快检吞吐只用于断流淘汰；`Fast`/`Key` 只由用户主动要求的完整持续下载测速授予。

## 24. sing-box 1.10+ 内核校验严格模式与老式快照语法冲突

**现象**：`sing-box check` 报错 `json: unknown field "statistics"`、`json: unknown field "server"`、`json: unknown field "type"`。
**原因**：
- sing-box 1.10+ 废弃了 `experimental.statistics`。
- `dns.servers` 的语法在现代 sing-box 中全面统一为 `address: "..."`（如 `address: "8.8.8.8"`、`address: "tls://223.5.5.5"`），不再接受 `type: "udp"` 与 `server: "8.8.8.8"`，且移除了 `domain_resolver`。
- `tls.utls.fingerprint` 严禁填 `"custom"`，必须回退至官方支持的 `"chrome"` / `"firefox"` 等。
**对策**：
- 导出或检测前必须执行 Schema 洗炼：
  - `clean_node_for_singbox()` 过滤不支持的协议（`xhttp`、`anytls`、`mieru`、`shadowsocksr`），剥离 `tls_tricks` 与未知字段，归一化 fingerprint；
  - 导出时自动清理 `experimental.statistics` 与旧式 DNS 字段。

## 25. 前置代理穿透泄露检测（Leak Guard）

**现象**：测试落地节点时，节点虽然返回了 IP，但实际上并没有连通远端节点，而是直接从前置代理（Karing）自身的出口出网了。
**原因**：当代理软件配置不当或前置跳板转发退化时，流量被本地前置代理直接代为转发到公网，未能经过远端落地节点。
**对策**：
- 测试启动前必须先获取本地前置代理的“基线出口 IP”；
- 凡经前置跳板测试的节点，其返回出口 IP 若与基线出口 IP 100% 相同，必须立即标记为 `前置穿透失败(出口等于前置本地出口)` 并淘汰，杜绝假落地。

## 26. ThreadPoolExecutor 非守护线程导致主程序结束时死锁假死（Python 退出挂起）

**现象**：终端控制台已完整输出“全部处理完毕”和节点明细表格，但 Python 进程一直停留在后台占用资源，终端光标不返回提示符，用户只能手动 Ctrl+C 或通过任务管理器强制杀进程。
**原因**：
- Python 标准库 `ThreadPoolExecutor` 创建的所有工作线程默认均为**非守护线程（`daemon=False`）**。
- 在批次测试中，即使调用了 `pool.shutdown(wait=False, cancel_futures=True)`，此前各批次中部分阻塞在底层 Socket 握手或系统 DNS 查询（`getaddrinfo`）上的工作线程仍继续存活。
- 当 `main()` 函数执行完毕调用 `sys.exit()` 时，Python 解释器在退出前会自动执行 `threading._shutdown()`，对所有未退出的非守护线程逐一调用 `t.join()`！若某个线程阻塞在网络 IO 上，解释器将被无限期卡死在退出阶段。
**对策**：
1. **显式使用 `os._exit()` 立即终止进程**：在脚本主入口 `if __name__ == '__main__':` 处，在刷新标准输出流后直接调用 `os._exit(ret)`：
   ```python
   if __name__ == '__main__':
       ret = main()
       sys.stdout.flush()
       sys.stderr.flush()
       os._exit(ret if isinstance(ret, int) else 0)
   ```
   `os._exit()` 直接在 C 运行时层面退出进程并释放全部 OS 句柄与网络连接，直接绕过 `threading._shutdown()` 的死锁等待。
2. **退出时优先强制关闭内核监听**：在批次上下文退出时，先执行 `proc.kill()` 切断内核进程，强行关闭本地监听端口，向正在进行 Socket 读写的存活线程触发 TCP RST 异常，促使其立即中断退出。

## 27. 本机正在使用的节点被判“出口与本机直连重合”而淘汰

**现象**：本机客户端（如 Karing TUN）正在使用某节点，本地测试时该节点却被淘汰为“出口与本机直连重合”。
**原因**：旧版用 Python 直接请求测跑机基线，请求被本机 TUN 接管，测到的是正在使用节点的出口；而节点测试走绑定物理网卡的 mihomo，绕开了 TUN，于是该节点出口恰好等于“基线”。
**对策**（已内置）：
- 基线经 mihomo DIRECT + 同一物理网卡测得，与节点测试同路径；系统路由出口只记录不作基线。
- 物理直连基线测不到时不做重合淘汰，并给出警告。
- sing-box 备用流水线在 TUN 接管系统路由时经物理直连中继出网，测试与测速不经过本机客户端当前节点。

## 28. 实际能流畅播放 4K 的节点测速却不达标

**现象**：节点在 YouTube 上流畅播放 4K（"connection speed" 先约 5 Mbps、后稳定 15 Mbps+），测速却只有 1~2 Mbps 或被判不达标。
**原因**：跨境高延迟链路上新建连接爬升慢，实测第 10~20 秒才到稳态；播放器用的是已"热"的连接并有缓冲。旧测速只看前 8 秒且要求每秒达标，把爬升期当成节点能力。
**对策**（已内置）：至少观测 10 秒、最多 20 秒，按最后 6 秒的稳态速度与 2 秒滑动最低值判定；正在爬升或贴近门槛的节点观测到 20 秒，贴近门槛再用新连接重测一次。
