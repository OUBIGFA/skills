# 代码工作约定

## 仓库整洁与跟踪边界

- 建仓或扩大项目结构前，先确定源码、可复现测试、构建发布、长期文档的目录职责；按需建目录，不堆空文件夹。
- 没有用户授权的情况下，严禁新建任何新分支。
- Git 跟踪源码、测试及脱敏夹具、依赖锁文件、构建/CI 脚本、许可证和长期文档；本地试验、日志、截图、缓存、下载、工具链与发布产物不入库。可复现测试属于正式项目，不能与临时试验一起忽略。
- 临时内容集中在 `_temp/<任务>/`；本地产物目录在生成前加入 `.gitignore`，禁止在根目录散落脚本、报告或安装包。
- 提交、打 tag、推送前检查 `git status`、暂存差异与跟踪文件清单，排除凭据、机器路径、缓存和二进制产物；只暂存本次相关文件。
- 提交信息沿用项目已有格式；项目无约定时用 `type(scope): 摘要`，类型取 `feat`、`fix`、`docs`、`chore`、`refactor`、`test`。
- 发布使用版本化 tag、统一构建入口和源码/资产校验；准备仓库不等于授权对外创建、推送或发布，沿用用户已有授权范围。

## 实施约定

- 先读相关实现和调用方，按影响范围调查；共享接口或来源不明时扩大搜索，不为小改动扫描全库。
- 面对不熟悉的需求，先主动搜索开源、活跃、维护良好的项目作参考，对照成熟实现再设计方案，不闭门硬写。
- 接口、命令与行为以查证为准，不作未验证的“认为”；同一思路连续失败即停下换路，查外部参考或询问用户，不陷入死循环。
- 优先修改已有控制点，复用共享的解析、验证和安全逻辑。保持清晰职责，不因行数机械拆分，也不顺带大规模重写。
- 生成文件不手改：代码生成产物、锁文件、快照等由工具维护的文件，改生成源并重跑生成步骤，不把产物当手写代码维护。
- 单次使用的逻辑先内联；只有被复用、封装真正复杂的边界或本身有清晰独立名字时才抽成函数。校验分支多时把细节下沉成小函数，主流程仍读作正常路径。
- 未知值只在拥有它的边界校验一次，向内传递已确定的类型；不重复 `typeof`、存在性检查，也不对 schema、构造函数或内部类型已保证的值再做防御性校验。纯同步的解析、校验和选项构造不为风格改成异步或副作用式接口。
- 修复根因并覆盖同类输入，不为单个样本硬编码；不添加静默降级、吞错或假成功旁路。
- 解法与问题同尺寸：优先采用能正确解决当前问题的最小充分方案，减少改动范围、新增概念、依赖和维护负担；“最小”不等于代码行数最少。
- 直改现有路径即可解决时（如补传数据、调整现有参数、增加必要兼容分支），不引入新抽象、新依赖或预留扩展点，不擅自升级为重构、框架、平台或治理系统。
- 新增抽象、配置、依赖或基础设施必须有当前需求依据，不能仅以“更通用”“更健壮”“以后可能用到”为理由。用户明确要求重构或通用能力建设时，按其授权范围执行。
- 为推测性或概率极低的竞态、安全边角、罕见输入增加复杂度前，先说明具体失败模式、发生概率和复杂度成本，取得用户同意；不为理论上的健壮性静默扩大改动范围。确有证据的失败模式仍按根因修复，不受此限。
- 改动反复返工、每修一处破另一处时，说明方案本身有问题，停下重新设计，不在错误方案上继续叠补丁。
- 写代码必须写注释：说明意图、约束与取舍，不逐行复述代码；公开接口、非直观分支和临时方案处必须注明原因。
- 保护用户已有改动；同步受影响的接口、引用和必要产物。检查差异，避免无关格式或编码变动。
- GitHub 仓库一律在 .gitignore 中全局排除任意层级下的 "_temp" 目录及其全部内容（含子目录）；该规则置于所有 `!` 保留规则之后，否则会被覆盖。已被跟踪的用 `git rm -r --cached` 移出索引，磁盘文件保留。
- 用可观察行为验证：故障可复现时加入回归测试，兼容性修复覆盖失败样本、同类输入和正常输入。配置、文案等选择相称检查，不为流程删除已完成实现。
- 测试公开行为、输出或产物，避免用源码文字匹配代替行为测试，除非文字本身就是契约。
- 少用 mock 和替身，测试真实实现；不把实现逻辑复制进测试，示例与预览使用真实生产组件而不是近似副本。写测试前先看项目已有的测试约定和相邻的同类测试。
- 完成实现后运行必要流程、检查结果、修复本次失败并复验。证据对应当前文件及相关环境；未变化时不因换一条回复重复执行。
- 用项目定义的统一检查入口（脚本、任务或 CI 配置），不绕过它直接调用底层工具；局部迭代只跑受影响范围，交付前跑全量。项目脚本与官方工具结论不一致时以官方工具为准，并记录差异。
- Windows 桌面界面测试必须在独立的私有桌面中运行，不切换用户当前桌面，不抢前台、焦点、鼠标或键盘，也不操作用户正在使用的应用实例。测试程序、驱动与截图在同一私有桌面中运行，使用独立测试数据；结束后仅关闭本次测试进程并释放桌面。隐藏窗口或在当前桌面后台发送消息不等同于私有桌面隔离。工具不支持私有桌面时，继续完成不依赖界面的验证，说明桌面验收阻碍；不得自行退回前台测试，除非用户明确授权本次例外。
- 构建只证明可构建，测试只证明已测行为，差异只证明改动范围。无法验证的部分明确说明，不能宣称已完成。
- 用户要求完整交付时给出可用的完整文件，不用占位符代替必要内容；长产物写文件，不机械等待“继续”。

## 解释与交付

- 先说明用户可见的变化，再给出相关文件和验证结果。用短句、明确动作和一致术语表达；面向非专业读者时解释必要术语，保留判断所需的技术依据。
- 用具体触发条件和修改前后的行为解释问题。验证说明包含检查对象、方法与实际结果；附必要命令或文件位置，区分已验证、推断和未覆盖范围。
- 跨模块依赖、调用顺序或数据流用短文难以说清时配图。小型静态关系图优先用 Mermaid；分别标明依赖、调用或数据传递的含义，用实际符号和文件位置支持关键连线。简单改动用文字即可。
- 图中分开呈现现状与方案，未知关系标明待验证。交付前核对图文与当前代码一致；语法或渲染通过不等于关系已查证。

专项清单审查时读取 [review-checklist.md](references/review-checklist.md)，普通编码不额外加载。
