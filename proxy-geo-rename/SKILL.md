# proxy-geo-rename：代理节点出口地理检测与统一重命名

## 核心原则

判断节点在哪，唯一可靠的办法是**真实通过它上网**，看它访问网站时用的公网出口 IP，再对这个 IP 做多方交叉定位。节点名、服务器地址（入口）都不可信——入口与真实落地出口经常不在同一个国家。检测不出来的节点**保留原名，绝不硬猜**。

## 前提与适用范围

- 目标配置为 **sing-box 格式 JSON**（含 `outbounds`）。Clash YAML 需先适配解析层，见文末"局限"。
- 需要：Python 3 + requests 库、**本机已有的 sing-box 内核**（不要为此下载安装新工具，先找本机现成的，见步骤 0）。
- 检测会通过每个节点发十几个小请求（每节点几十 KB），38 个节点约 2~5 分钟。

## 工作流程

脚本都在本 skill 的 `scripts/` 目录，按顺序执行。`<workdir>` 建议用配置文件同目录下的 `proxy-geo-work`。

### 步骤 0：环境侦察（每次都先做）

1. **找本机 sing-box 内核**（用户装有代理客户端时本机几乎必有，严禁擅自下载）：
   - 查运行中的进程：`Get-Process | Where-Object {$_.ProcessName -imatch "sing|clash|mihomo|v2ray|xray|neko|hiddify|karing"} | Select-Object ProcessName,Path`
   - 搜常见目录（LOCALAPPDATA\Programs、APPDATA、Program Files、Desktop、Downloads、用户的工具盘）：文件名匹配 `sing-box*.exe`、`*neko*core*.exe` 等
   - 找到后 `<内核> version` 确认可执行；1.10~1.13 均已适配
2. **查 TUN 全局接管**：`Get-NetAdapter | Where-Object Status -eq Up`。若有 TUN 虚拟网卡（如 "Karing TUN"、"Meta"、"sing-box"），记下**物理网卡名**（如 WLAN、以太网），必须传给 `--iface`，否则测试流量会被现有代理污染、且本机直连测量结果不可信。
3. 确认 `python -c "import requests"` 可用。

### 步骤 1：主检测

```
python <skill>/scripts/probe.py --config <配置.json> --singbox <内核路径> --iface <物理网卡> --workdir <workdir>
```

自动完成：生成测试配置（每节点一个本地端口）→ 自动剥离旧内核不认识的字段/回退不支持的指纹取值 → 并行通过每个节点向 5 个地理源查询（Cloudflare trace、ip-api、ipinfo、MaxMind/ip.sb、ipwho.is）→ 失败源用本机直连反查出口 IP 补票 → 第二轮复测出口稳定性 → 投票判级。产出 `probe_result.json`。

### 步骤 2：二次复核

```
python <skill>/scripts/recheck.py --workdir <workdir>
```

三重复活机制依次执行：① 离线节点低并发重试（首轮 8 并发抢带宽可能误伤 UDP 类节点）；② 仍离线的节点自动探测本机正在运行的代理客户端端口（karing/Clash Verge/v2rayN 等，SOCKS5 优先），**经中转再测一次**——节点服务器 IP 从本机直连被墙但节点活着是常见情况（用户客户端 TUN 环境下走隐性中转所以"能用"），中转不影响出口判定，复活节点标注"直连被墙"；③ 出口漂移节点采样出口池。之后对全部出口 IP 增补 3 个地理库（ipapi.co、ipapi.is、freeipapi）+ RIR 注册国参考（只展示不计票），统一重投票。产出 `probe_result_final.json`。**直连+中转都不通的节点才是真死节点。**

### 步骤 3：解读结果，存疑节点做延迟仲裁

高置信（票数≥4 且领先明显）可直接命名。若仍有中/低置信节点（典型原因：数据库分歧 IP，多个库各说各话），运行：

```
python <skill>/scripts/latency_arbiter.py --workdir <workdir> [--region eu]
```

它会自动带上一个高置信节点做**标定**，再测存疑节点到各城市锚点的真实 TLS 握手耗时。解读要点：

- 先看标定节点：最近锚点应与其已知位置相符，由此确认锚点有效；同节点内 **<40ms 的锚点差在噪声内不可采信**，明显梯度（>60ms）才算数
- 排除法优先：欧洲各锚点耗时紧凑（互差 <60ms）即可排除美洲/亚洲，反之亦然——跨洲差异（±180ms 级）永远清晰，相邻城市（如法兰克福 vs 维也纳，差 ~16ms）无法区分
- 结合 Cloudflare 接入机房（colo）：出口若真在维也纳，anycast 会就近接 VIE 机房；接的是 FRA 则物理更近法兰克福
- **裁决原则**：地理库有明确多数（≥3 票且供应商标注一致）→ 从多数（这是网站眼中的位置）；库无多数 → 从物理证据（colo + 延迟梯度）

把终裁写入 `<workdir>/overrides.json`：

```json
{"节点原名": {"cc": "DE", "country_zh": "德国", "city_zh": "法兰克福", "note": "库五说各异，物理测距终裁"}}
```

### 步骤 4：预览重命名

```
python <skill>/scripts/rename.py --workdir <workdir> [--overrides <workdir>/overrides.json]
```

默认 dry-run 只打印对照表并写 `rename_map.csv`，不动原文件。检查：编号分组是否合理、有无该仲裁未仲裁的低置信节点、离线保留名单。

### 步骤 5：确认后写回

```
python <skill>/scripts/rename.py --workdir <workdir> [--overrides ...] --apply
```

自动：备份原文件（`<原名>.backup.<时间戳>.json`）→ 改节点名并**同步全部引用**（selector/urltest 成员、default、detour、route 规则、dns detour）→ 保持原文件换行风格写回 → 校验（JSON 合法、无重名、引用完整）→ 产出 `report.md` + `rename_map.csv`。

### 步骤 6：交付

向用户报告：命名汇总（按地区分组）、名字与实际不符的节点（重点）、双出口/分流节点、离线名单与处理建议、备份位置、"客户端需重新导入配置才显示新名字"。

### 步骤 7：若用户要把配置导回客户端

先判断手上的配置**是不是客户端的运行时快照**——同时含 `inbounds` + `experimental` + fakeip 类 DNS 即可断定。这类文件直接导回客户端会与客户端自身的端口/组件冲突，表现为**几乎所有节点都显示不可用**（与节点本身无关，极易误判为改名改坏了）。此时用：

```
python <skill>/scripts/make_profile.py --config <配置.json> [--exclude 死节点A,死节点B]
```

它只保留节点本体 + 一个自动测速组与选择组，剥离节点上指向快照内部 DNS 标签的 `domain_resolver`，入站/DNS/路由交给客户端生成。客户端定制字段（`tls_tricks` 等）原样保留——官方内核校验报未知字段属正常。

## 判定规则（verdict.py 实现，调整前先读懂）
- 计票源 = 各独立地理库（同库家族只算一票；`ref:` 前缀的注册地信息不计票）
- Cloudflare 接入机房（colo）所在国家计 **1 张物理决胜票**
- 票数≥4 且有效领先≥2 → 高置信；票数 3 视领先与 colo 佐证定高/中；更低 → 低置信
- colo 与判定国跨大洲 → 高置信降为中（分流节点常见，不否决）
- 城市：同国来源的城市名归一化聚合（中英文/全称简称同桶，如 Warsaw/华沙/Frankfurt am Main），多数票 > 接入机房城市 > 单源，城邦（HK/MO/SG）城市即地区名
- ip-api 的中文城市名**仅当其国家判定与多数一致时**才可采用（防"借用异国城市名"）

## 命名规则

- 格式：`{国旗emoji} {中文地区名}_{城市}_{编号}`，如 `🇯🇵 日本_东京_8`（国旗与国家名之间是空格，其余用下划线）
- 国旗由 ISO 两位码用区域指示符自动拼出（`geodata.py` 的 `flag()`），无需维护表；极少数取不到国旗的情况退回 `{ISO码}_` 前缀，保证仍能一眼看出地区
- 编号按（国家+城市）分组、按配置文件内原顺序从 1 递增
- 城市无通用中文译名的小地名保留英文原文（报告注明），不硬造译名
- 国家中文名用规范简称（俄罗斯、韩国），不用地理库的官方全称
- 离线、低置信未终裁 → 保留原名并在报告单列
- 检测结果与配置节点靠**指纹（协议|服务器|端口）**关联，不靠名字——客户端可能在检测前后自动改名（karing 会加国旗前缀），重跑 rename 依然对得上号

## 排序规则

节点默认**按地区聚成块**写回配置，同时同步各分组的成员顺序——客户端界面按配置顺序展示，排好序后同一地区的节点才会挨在一起，不会东一块西一块。

顺序按使用习惯从近到远：港澳台 → 日韩新 → 东南亚/南亚 → 中东 → 北美 → 西欧北欧 → 中东欧 → 大洋洲 → 南美 → 非洲，未识别地区（离线、低置信、`🏳️ 未知`）一律垫底，避免打断已归类的分块。顺序表是 `geodata.py` 的 `REGION_ORDER`，表里没有的地区排在已列出地区之后。编号在排序后重新分配，所以同一地区内编号连续。

需要保留配置原有顺序时给 `rename.py` 加 `--no-sort`。

## 合并多个订阅并去重

多个订阅合成一个库时用：

```
python <skill>/scripts/merge_configs.py --base <底库.json> --add <订阅1.json> <订阅2.json> [--apply]
```

默认预览，`--apply` 才写入；写入前自动备份底库。合并完还会顺手做统一命名与地区排序（合并后正是要做的事），只想合并加 `--no-rename`；想保留底库不动、结果另存加 `--out <新文件.json>`。

**去重看的是「连接身份」**——协议 + 服务器地址 + 端口 + 凭据（密码/UUID）+ 传输方式 + SNI，全都相同才算同一个节点。不看名字，因为同一节点在不同订阅里名字往往完全不同（`秘鲁_🇵🇪_youtube@资源分享师_PE_124` 和 `🇵🇪 秘鲁_1` 其实是同一个）；也不能只看地址端口，因为同址同端口但凭据不同是真的两个节点，误删会丢线路。

底库自身已有的重复也会一并清理（引用自动改指向保留的那个），`--keep-base-dup` 可关闭。合并时另外处理三件事，避免并进来就坏：源配置里指向自身 DNS 标签的 `domain_resolver`、指向未一起并入的前置节点的 `detour`，这两类悬空引用会被摘除；与底库撞名的 tag 先临时加后缀区分，随后统一改名时消化掉。

## 只排序不检测

节点名已经带地区信息（国旗/中文国名/ISO 码）、只是命名杂乱或顺序混乱时，不必跑完整检测：

```
python <skill>/scripts/sort_nodes.py --config <配置.json> [--apply]
```

它从现有名字解析地区与地名，按同一命名格式重排重编号：能认出的真实地名（台北、横滨、华沙…）保留城市段，认不出就省略；`AI`/`USAI`/`❇️`/`家宽` 等自定义标记原样保留在编号之后；来源与协议标记（极限白嫖、vless-reality、阿里云…）视为噪音丢弃；认不出地区的归入 `🏳️ 未知` 排在最后。加 `--keep-names` 则只调整顺序不改名。

注意它**只是整理名字，不核实归属地**——名字本身就标错地区的（如挂 🇨🇳 旗却写台湾）它只能按文字判断。要确认真实落地，仍须走 probe.py 的检测流程。

## 实战经验（重要，动手前浏览）

遇到异常现象先查 `references/troubleshooting.md`——包含 TUN 污染识别、代理"延迟拨号"假握手、旧内核字段兼容、Anycast 双出口、数据库分歧 IP 等 10 余条实战踩坑与对策。

## 局限

- Clash YAML 配置：方法论完全相同，但需适配解析/写回层（节点在 `proxies`，引用在 `proxy-groups[].proxies` 与 `rules`）；改 `probe.py` 的 `load` 与 `rename.py` 的写回部分，其余复用
- 找不到 sing-box 内核但有 mihomo：需把节点转换为 Clash 格式用 mihomo 测（未预置，现场适配）
- 延迟仲裁锚点（DataPacket 城市端点）可用性会变化，脚本运行时自动跳过失效锚点；某大洲全部失效时更换 `geodata.py` 的 ANCHORS 表
- 经中转复活（via_front）的节点不做延迟仲裁（中转链路噪声大且测试端口随中转内核关闭），其判定依赖多库投票——直连型 VPS 出口即服务器 IP，通常票数很足
- ip-api 免费版仅支持 http（非 https），属正常现象非错误
